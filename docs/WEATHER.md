# Weather sources

Updated 2026-10-11. Weather is off by default. Development and CI use synthetic forecasts; neither automatically requests the user's location.

## Choosing a point

Unconfigured weather is hidden from the menu bar. A saved valid point keeps the weather item stable while forecasts are off, stale or unavailable. Weather Settings offers three point inputs: manual coordinates, explicit city/ZIP search through Apple's geocoder, or **Use My Mac Location** through macOS Location Services. Search sends its query and network IP to Apple; the Mac action may prompt for OS permission and requests one point with coarse desired accuracy. No reverse geocoding, background tracking or IP geolocation is performed. Requests time out after 20 seconds, are replaced by a newer action and are cancelled on close/minimization. Ambiguous results require a choice. Public tests inject providers and never request a real point or grant.

A choice stages weather coordinates and, optionally, offline daylight coordinates/time zone. It does not enable forecasts, maps or daylight. Apply saves the draft; each service has its own switch and disclosure. macOS permission persists independently of cancelling a request or clearing a point. Apple geocoding and macOS location availability need real consented validation; synthetic cancellation/selection tests do not establish service availability.

## Open-Meteo forecast adapter

[Open-Meteo terms](https://open-meteo.com/en/terms) permit the free hosted service for personal/noncommercial use, within the documented request limits. The app refreshes at most every 15 minutes for one chosen location. The provider abstraction allows a different compliant backend later. Calling the REST API does not incorporate its server source code.

Data attribution is displayed as Open-Meteo with a link; forecast data is licensed under CC BY 4.0. Current conditions are model-derived estimates, rather than local station observations. Quality and resolution vary by region, model, terrain, and forecast lead time. The service offers regional models including NOAA HRRR in supported US coverage; selecting a model is a later option.

Opt-in discloses IP and coordinate transmission and coordinate-bearing troubleshooting logs which the provider may retain up to 90 days. Chosen coordinates are rounded to two decimal places before forecast requests. The point can be entered manually, found by an explicit city/ZIP search, or chosen with a one-shot macOS location request. No credentials are required.

Forecast Unix timestamps remain absolute instants. Hourly and daylight times use the returned location timezone with daylight saving adjustments. Daily labels retain the response's fixed-offset forecast-day boundaries so a transition cannot relabel a day as the previous date. Missing or invalid timezone metadata uses a disclosed fixed-offset fallback, or UTC when no valid offset exists. Current condition icons use reported WMO codes and the optional `is_day` flag. Missing daylight metadata uses a neutral icon; unknown conditions remain explicit. NWS observations use recognized metadata from their published icon identifiers; Aerie draws native symbols without downloading those assets. Unknown or mixed identifiers retain an unavailable icon rather than inferring one from free text. See [NWS icon-code descriptions](https://api.weather.gov/icons). See [provider timestamp documentation](https://open-meteo.com/en/docs).

## NWS observations and forecasts

[NWS API documentation](https://www.weather.gov/documentation/services-web-api) describes its free public API, application-identifying User-Agent, rate limits and geographic coverage. Aerie supplies its own User-Agent and uses only `api.weather.gov` over HTTPS. It requires no credentials. Manual forecast consent sends the rounded point and IP to that selected provider; no automatic provider fallback occurs. Unsupported points, unavailable products and response failures stay explicit.

Each refresh discovers the advertised forecast grid, hourly forecast and station list. At most the nearest three valid advertised stations are considered, requesting quality-controlled latest observations. Values are interpreted only with recognized source units. Missing values remain unavailable. Observations more than 90 minutes old or more than five minutes in the future are withheld; source station and observation time remain separate from forecast issuance and validity. Provider delay is possible, and station conditions need not match the manual point. Forecasts can remain available when observations fail.

Named day/night periods retain source start/end times, conditions, wind and detailed narrative; their temperatures are not represented as complete 24-hour minima/maxima. Hourly values retain missing temperatures and location timezone/DST. The native period view presents the exact source validity range. Current NWS alert messages query only the rounded point, independently of forecast periods, preserve all message/event timestamps and offer bounded native details. Point scope does not establish complete area coverage. Alert failures, an empty response and additional provider pages remain distinct; no extra pages are fetched. Forecast and alert polling is once per 15 minutes and is not an immediate alert delivery system.

There are at most eight sequential requests per refresh, with no immediate retry. Both forecast providers reject oversized declared bodies and stop unknown-length or decompressed response chunks before exceeding 2 MB; redirects cannot switch providers. Sessions are ephemeral and close on success, failure or cancellation. Forecast detail windows make no additional requests and clear text on close. NWS source attribution is visible under its [public-data disclaimer](https://www.weather.gov/disclaimer); Aerie does not imply NOAA/NWS endorsement. Maps have independent consent and lifecycle rules below.

The development command `Aerie --nws-integration-fixture` checks forecast availability using a fixed public documentation point without reading user preferences. It prints only counts and availability summaries, and is not run by public CI. Automated tests intercept transport using synthetic JSON and exercise bounds, cancellation, nulls, units, DST, stale observations and independent product failures. This does not establish native rendering or live consent acceptance.

## Cached hourly details

Hourly rows are selectable, with a configurable presentation bound of 24, 48, 72 or 168 current/upcoming periods. Detail windows use the existing report and issue no new requests. Missing-temperature hours remain visible. Probability of precipitation is separate from amount; neither implies rain rather than snow.

[NWS schema documentation](https://api.weather.gov/openapi.json) defines hourly validity windows, humidity, dewpoint, wind and gust fields. Aerie accepts recognized quantitative units or keeps published textual wind ranges; unknown units remain unavailable. Window endpoints retain their distinct timezone offsets through repeated daylight-saving hours. NWS does not supply every detail shown by the generic view.

The [Open-Meteo forecast schema](https://open-meteo.com/en/docs) supplies requested hourly feels-like temperature, humidity, dewpoint, wind/gusts/direction, surface pressure, cloud cover, precipitation amount, UV and visibility where available. Requests explicitly select Celsius, km/h and millimetres. Hourly precipitation amount/probability and maximum gust describe the preceding hour; details show that window separately from instantaneous fields. Optional short/null arrays preserve missing values without shifting neighbouring hours; invalid percentages/directions/nonnegative quantities are withheld. The model adapter retains at most 384 hourly entries and the same 2 MB receipt bound, ephemeral session, provider consent and 15-minute fetch cadence. No provider requests are made by public tests. Native detail interaction, enabled-source cost and coverage remain unvalidated.

## Detailed maps milestone

The native AppKit window loads only on demand and releases requests, animation timers, raster frames, and rendering state when closed. Idle/background footprint keeps the strict all-process budget. Active map use may have reasonable temporary headroom; measure its peak and verify prompt return close to baseline after close, including repeated open/close cycles. A bounded frame cache and timestamps/legends are required.

| Layer | Source direction | Coverage and distinction |
| --- | --- | --- |
| Observed radar and storm tracking | [NOAA radar GIS](https://opengeo.ncep.noaa.gov/geoserver/www/index.html), MRMS and supported station products | US products; observed reflectivity is separate from forecast precipitation. Storm tracks need a verified track product or clearly labeled derived analysis. |
| Satellite | [NOAA nowCOAST](https://www.nauticalcharts.noaa.gov/learn/nowcoast.html) time-enabled WMS | Validate current service layers, bands, timestamps, and coverage. |
| Official alerts | [NWS API](https://www.weather.gov/documentation/services-web-api) and NOAA warning GIS | US official alerts; source and issuance/expiry times must be retained. |
| Temperature, wind, rain, snow forecasts | [NWS CloudGIS/NDFD](https://www.weather.gov/gis/cloudgiswebservices) | Forecast valid time and accumulation period must be explicit. Services and layer names still require implementation validation. |

NOAA public data is available without paid credentials, but basemap licensing and per-layer attribution must be verified before use. The adapters and native controls are implemented. The manual developer integration command uses a fixed public CONUS extent; public automated tests use synthetic XML and intercepted synthetic requests. Real visual and post-close footprint validation still needs an unlocked Mac. Convective-cell tracks and richer per-polygon alert inspection remain open. No web view is used.

## Map consent, data and resource behavior

NOAA maps have a separate opt-in in Weather Settings and use the chosen location. Forecast opt-in is independent. Opening a map sends the selected map extent and IP to the selected NOAA/NWS service. Opening alert details also sends the rounded map-center point to NWS. Maps are off by default; old settings decode with maps off, and import/export clears saved points and source consent. Maps do not request a device location; only the separate explicit Settings action can do so. No third-party basemap or API key is used.

[NWS usage terms](https://www.weather.gov/disclaimer) permit its public-domain data unless a product says otherwise, require source identification and prohibit implying endorsement. The selected NWS state-boundary service identifies its copyright/source as NOAA/NWS; no external commercial basemap is incorporated. Source attribution remains visible. Service coverage varies: US radar and NDFD, GOES regional or global satellite mosaics, and NHC tropical-cyclone tracks. Tropical past/forecast tracks are distinguished from convective-cell tracks, which remain unimplemented.

Time-enabled radar, satellite and forecast layers use advertised service times, including bounded start/end/period intervals. Expired-only or empty time-enabled products show unavailable state and the latest advertised time when known; they never request an undated default image. Calendar-month/year time intervals are unsupported and fail metadata validation. Genuinely timeless products explicitly state that the service supplies no valid time and display fetch time. WMS 1.3 axis order is explicit. Precipitation and snow products are six-hour accumulations ending at the selected valid time, in the provider's source units. Legends come from the provider; long legends scroll without shrinking text. The tropical-track legend shows the first selected forecast-track layer; fuller per-track advisory presentation remains open.

The primary alert map and optional overlay use NOAA's advertised `WatchesWarnings` WMS product, covering its current US watches, warnings and advisories. The `CurrentWarnings` product's five severe-warning types remain an optional service variant. [Official layer metadata](https://mapservices.weather.noaa.gov/eventdriven/rest/services/WWA/watch_warn_adv/MapServer/1?f=pjson) documents the product. REST IDs may differ from WMS layer names, so selection uses the advertised product title rather than a hardcoded number. The overlay always shows current polygons and its own fetch time, independently of historical radar or future forecast frames. It does not represent alert validity at the selected base-layer time. The native alert-detail view fetches current NWS messages at the rounded map-center point on demand. It preserves message sent, effective, onset, message expiry and event end times separately, plus issuing office, severity, urgency, certainty, description and instructions. A point query does not establish complete polygon coverage across the map extent. Empty, truncated and unavailable responses remain distinct. At most 100 messages and 2 MB of response data are accepted; the HTTP client rejects oversized declared lengths and stops unknown-length bodies before appending beyond that bound; truncation/pagination is disclosed and no additional pages are fetched automatically. Closing the detail view cancels its request; closing the map releases the detail window and its text. Richer per-polygon inspection remains open.

A map window owns its ephemeral HTTP session, cancellable jobs, 120-second visible-window refresh, user-started animation, metadata and decoded raster cache. Metadata refresh preserves the selected service variant, eligible valid time and playback intent. Minimize, app hide, complete window occlusion and system sleep suspend both timers, cancel requests (including paced requests), and release raster caches and view images. Reactivation refreshes metadata and resumes playback only when eligible frames remain. Requests are spaced by at least 750 ms, with no immediate failure retry. Playback uses at most 12 cached frames, within 16 MiB of conservative decoded RGBA cost; boundary/alert/legend images are separately bounded by image dimensions and response size. Closing cancels requests/timers, removes observers and clears every view image/cache. Synthetic tests verify lifecycle transitions, selection preservation, request suspension/reactivation and cache release; this does not substitute for repeated real-window footprint checks.

The explicit development command `Aerie --map-integration-fixture` checks real service metadata, rasters and legends using a fixed public CONUS extent. It does not read user settings and is not run by public CI. State boundaries resolve the service's advertised title and coordinate systems instead of assuming a numeric layer ID. Legend requests include the advertised style, bounded symbol-size hints and labels. Symbol sizes come from the legend resource's request parameters; the advertised final image size is a different quantity. Only numeric hints are copied, and requests always use the allowed HTTPS service endpoint. Blank accessory images are treated as unavailable; transparent weather or alert rasters may still represent valid empty data. Horizontal legends use the full map width, while vertical legends scroll in the sidebar. Both release on suspension and close. The native application menu supports Hide Aerie (Command-H) for map suspension.
